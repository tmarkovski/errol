# Errol

Relays a conversation between the OpenAI Codex desktop app and Claude Desktop on macOS by automating their UIs: it presses each app's "Copy" button and pastes the response into the other app's composer, exactly like a human relaying messages between two chat windows.

It is a menu bar app: an owl sits in the status bar, and clicking it opens a floating panel where you type the instruction that seeds the conversation and press Start. There is no CLI; the panel's Inspect button covers the selector debugging the old command-line flags used to.

Named for the Weasleys' owl: not the fastest courier, has been known to hit the wrong window, but the message always gets delivered. (The naming candidates that lost are recorded in `docs/brand-exploration.md`.)

## What we're building and why

An experiment in having two AI assistants talk to each other **as products**, not as raw models. Going through the desktop apps means each side keeps its own system prompt, tools, memory, and subscription context. There are no APIs or SDKs involved anywhere; the entire mechanism is the macOS Accessibility API (`AXUIElement`) plus the system clipboard and synthesized keystrokes.

**Design decision: the desktop apps are the point, not a workaround.** A CLI-to-CLI version (`claude -p` piped into `codex exec` in a loop) was considered and rejected. It would be simpler (no permissions, no clipboard, no focus stealing), but it talks to the bare models. This project specifically wants each side operating inside its app: Claude Desktop with its projects, connected tools/MCP servers, memory, and settings; Codex with its threads, skills, and workspace context. The UI relay is the only way to get that, so the added fragility is accepted. Do not "simplify" this into a CLI pipeline.

## How it works

The conversation is framed for both participants before the relay goes hands-off. The first agent receives the ground rules (this is an agent-to-agent conversation, the human is not participating, and it can sign off by including the stop sequence, default `[[END-CONVERSATION]]`) followed by the instruction typed into the panel. The rules also push back on the single-shot habit — treat this as a multi-turn dialogue, contribute incrementally, and never *initiate* the sign-off in a first reply ("initiate" so that reciprocating a peer's early sign-off stays allowed) — because in early live runs both models would answer the seed completely in one message and immediately sign off, especially on brainstorm-shaped tasks. Pacing beyond that baseline belongs in the instruction text, where it stays visible and editable per run — the panel's conversation shapes carry purpose-specific pacing (a brainstorm demands rounds of divergence before converging), and the live relay test's seed demands three replies per side. When the first response comes back, the second agent receives the same rules plus both the initial message and that response, so both sides start from identical context. Every message after those two framing messages passes through verbatim. Ending is a handshake: a reply containing the stop sequence is still relayed, so the peer sees the goodbye and can answer with its own — the run closes when two consecutive replies carry the marker (the rules tell each agent to reply to a sign-off with one of theirs). An empty reply ends the run immediately, since there is nothing to relay. Each side's card in the panel shows its conversation status underneath the surface line — "Not started", "Chatting…", "Waiting", or "Conversation ended" (only a real sign-off leaves "ended" showing after a run).

One turn of the loop:

1. Wait until the current speaker finishes its response. Completion is detected when **no "Stop" button** is visible (still streaming), any of three signals says a response landed, and that state holds for two consecutive polls. The signals, in order of precision: a **new per-message affordance** beyond the baseline (an affordance is a mounted copy button *or* — on Claude Code, where the action bar stays unmounted until hovered — the collapsed "Show message actions" toggle standing in for it; each rendered message carries exactly one of the two, so the count is a message count); the newest message's **ordinal** advancing far enough past the baseline to be the response — Claude names every message "Message N", and the newest is always mounted; and the **streaming transition** — the Stop button was observed and has gone, so the response it belonged to is complete whatever the counters claim. Three signals because the count alone hung a real run (Aug 28 2026): Claude **virtualizes** long conversations, unmounting older messages as new ones land, so the affordance count plateaus or falls — the stuck run's baseline was 7 with the finished response on screen and only 3 affordances mounted, a threshold no response could ever cross. The ordinal survives virtualization but only exists where messages are numbered; the streaming transition is the app-agnostic backstop for everything else. On Claude, the just-pasted user message grows a counted affordance of its own, so right after sending, the relay waits for that echo and folds it into the baseline; only affordances beyond it can belong to the response. On ChatGPT the echo mounts "Copy message", which the copy selector excludes — nothing to absorb, and the wait is skipped (`echoCountsAsAffordance`): waiting there would misread any response that completes inside the wait window as the echo and fold it into the baseline, leaving the relay waiting forever (the Codex-mode fast-reply race below).
2. Press the last copy button in the tree (newest message) and confirm the press landed by watching `NSPasteboard.changeCount`. When the newest affordance is the collapsed toggle instead, press it first and wait for the bar's copy button to mount — the AXPress equivalent of the hover that normally expands it.
3. Bring the other app frontmost and verify it actually got there (see safeguards), focus its composer (`AXTextArea`), synthesize Cmd+V, wait for the paste to render, press the send button.
4. Swap speaker and listener. Repeat until both sides sign off (or the optional turn cap).

Both apps are Chromium-based, and Chromium exposes an empty accessibility tree until nudged, so `AXManualAccessibility` is set on both at the start of each run. Everything runs against label-based selectors, kept per app in `AppSelectors` structs inside `Config` because they are the part most likely to break. The labels differ between the apps: ChatGPT calls per-message copies "Copy message" (bare "Copy" is code blocks, "Copy table" is tables), while Claude uses "Copy" with excludes.

Safeguards discovered the hard way:

- **Verified activation.** From a background process under macOS cooperative activation, `NSRunningApplication.activate` returns true without effect and setting the AX `kAXFrontmostAttribute` returns success without effect; LaunchServices (`/usr/bin/open -b`) is what actually brings an app forward. Synthesized keystrokes go to the frontmost app regardless of AX focus, so the relay confirms the target is frontmost before typing — via the system-wide AX focused application, falling back to the window server's front window when the focused app's AX server won't answer (Electron apps go quiet intermittently) — and refuses to send keystrokes otherwise. Without this, the seed gets typed into whatever window the user last touched.

- **Verified paste.** Frontmost isn't enough for typing: synthesized keystrokes follow the *key window*, which can stay behind on another window (Errol's own non-activating panel among them) while the target app reads as active — the paste then lands nowhere and the relay presses Send on an empty composer (observed live, Aug 27 2026). After pasting, `send` waits for either the payload text in the composer or a newly mounted, composer-scoped pasted-text attachment chip. The second signal matters because ChatGPT turns long pastes into `pasted-text.txt` while leaving the text area's AX value at its placeholder; treating that as a miss pasted the same attachment twice (observed live, Aug 30 2026). Only when neither signal appears does Errol force a LaunchServices activation (the one call that also moves key status) and paste once more before warning.

- **Window scoping.** All searches run inside one chosen chat window per app, re-resolved on every poll. Claude Desktop can host Claude Code sessions whose windows contain their own "Copy" and "Stop" buttons — including, if you develop this tool inside one, the session driving the relay. A window is classified by Claude's own world switcher: the top-level `AXRadioGroup` whose selected option names the mounted world, and a window showing "Code" is never chosen while any chat window exists (`excludedWorldName` in `Core/Config.swift`; the option appends live session state after a comma, e.g. "Code, awaiting your input", so only the name before it is matched). Marker labels ("Terminal input", "New terminal", "Rewind to here") remain as a backstop for builds with no switcher, ORed with it — an unrecognized Code session gets relayed into, while a wrongly excluded chat window only reports the wrong surface, so the two signals are combined in the direction that adds exclusions. When Claude Desktop has *no* chat window, a Claude Code session window with a composer is a deliberate fallback target (`excludedSurfaceIsFallback` in `Core/Config.swift`): the strip reports it Ready as "Code" and the preflight logs a NOTE naming what it will type into. That weakens the original never-touch-Claude-Code guarantee by choice — if the only session open is the one developing Errol, the relay will land in it, so leave the world switcher on Chat (or turn the fallback off) while developing. On the current single-window build that is the only way to have a chat window at all, which also means the NOTE fires on every run started from the Code world; it reports which world is being typed into, not a fault. The preflight still refuses when an app has no targetable window at all.
- **Send confirmation.** Sending prefers pressing the app's send button over a Return keystroke, then confirms the message actually left, escalating through Return and Cmd+Return before warning. Confirmation accepts either of two signals: the composer's value moved off the payload, or the send control dropped back to its empty-composer state — disabled on Claude Code, where the Send button is a persistent icon button (`AXDescription` "Send", disabled while the composer is empty), unmounted entirely on ChatGPT. The composer value alone is not trusted because it has been observed reading stale for seconds after a successful send on Claude Code (Aug 27 2026), which sent the old single-signal check through the whole keystroke escalation on a message that was already gone.

## Layout

Everything lives in the Xcode project at `app/Errol` (`Errol.xcodeproj`). Inside the app target:

- `ErrolApp.swift`: the `@main` entry point; a placeholder Settings scene plus the delegate adaptor that installs the shell.
- `MenuBarController.swift`: the AppKit shell — the status item and the floating panel hosting the SwiftUI view. It stays AppKit because the panel must be a non-activating floating panel (the Spotlight pattern): SwiftUI's `MenuBarExtra` window dismisses itself whenever another app activates, which the relay does on every turn, so the controls and log would vanish exactly when a run needs them visible.
- `ControlPanelView.swift` / `RelayController.swift`: the SwiftUI interface and its observable model — form state, the log, and the start/stop/inspect wiring around the engine.
- `Core/`: the relay engine, split by concern. `Config.swift` holds bundle IDs, label keywords, caps, and timings; `Accessibility.swift` and `Elements.swift` the AX wrappers and window-scoped element finders; `ElementNode.swift` the protocol the finders are generic over, with live-AX and recorded-fixture conformances; `Activation.swift` the verified-activation and refocus logic; `Arrangement.swift` the window tiling; `Keyboard.swift` the synthesized keystrokes; `RelayActions.swift` the copy/send/wait primitives; `Relay.swift` the message framing and the orchestration loop; `Inspect.swift` the selector-debugging dump; `Readiness.swift` the continuous scan behind the panel's readiness strip; `Logging.swift` the log, transcript, and the cancellation flag behind the Stop button.

Repo-level tooling lives in `tools/`: `ax-dump.swift` is a standalone inspector (`swift tools/ax-dump.swift claude --buttons`) that dumps the live accessibility tree of any running app from any shell holding its own Accessibility grant — no Xcode, no build step, and Errol doesn't need to be running. Its header comment documents the modes (summary fingerprint, full tree, button census, per-element attribute dump, menu bar, fixture-JSON capture) and the capture-and-diff workflow for developing detection heuristics.

## Testing

The detection contract is testable at several cost levels, and all of them run the production code — `Package.swift` builds the same `Core/` sources the app compiles (pointed at in place, no copies) as the **ErrolKit** library, which the test suite and the harness link. The Xcode app does not depend on the package and builds exactly as before; the package exists so the tools cannot drift from the app. Tools and tests reach ErrolKit's internals via `@testable import` (debug builds enable testability), so Core carries no public-API annotations for their benefit.

- **`swift test`** — contract tests, no apps needed, in two layers. The selector layer pins the pure label logic: copy-selector semantics per app (including the "Copy message" echo asymmetry that caused the Codex fast-reply race), the `echoCountsAsAffordance` flags, the send-button "feedback" trap, announcement parsing, surface-name precedence, and the relay's message framing, length cap, and stop-sequence contract. The scenario layer runs the *finders themselves* over recorded trees: the walk is generic over the `ElementNode` protocol (`Core/ElementNode.swift`), with live `AXUIElement`s and JSON fixtures as its two faces, so `tests/ErrolKitTests/Fixtures/` drives the identical detection code the relay runs. One fixture per screen the detection must classify — ChatGPT Chat/Work home (new chat) and open conversations (plugging into an existing chat), Codex mode, mid-stream; Claude Chat/Cowork home and conversations, a project chat, Claude Code with action bars collapsed and expanded, sidebar collapsed and expanded, streaming, and the old multi-window layout — each asserting the full verdict: chosen window, exclusion, surface, model, affordance count and order, send/stop/composer. Run these on every selector change. `ERROL_TEST_LOG=1 swift test` (off by default) dumps every scenario's tree shape, per-window classification, and detection outcome to stderr for debugging a failure.
- **`tools/ax-dump.swift <app> --capture`** — records the live windows' trees as fixture JSON. When an app update moves a tree, recapture the affected screens into `tests/ErrolKitTests/Fixtures/` and the scenario tests check the new shape against the whole contract. Three fixtures are real captures with sidebar conversation titles, project names, message text, and the account name anonymized — structure, roles, and counts untouched: the two home screens (`chatgpt-chat-home`, `claude-chat-home`, Aug 27 2026) and `claude-virtualized-conversation` (Aug 28 2026), the exact window of the stuck-relay bug — a long Claude Code conversation with only the last three of eight messages mounted, captured while the undetected response and sign-off were on screen. The remaining fixtures are synthesized from the live-verified shapes in the field notes below — replace them with real captures as screens get re-observed.
- **`tools/verify`** — the guided live harness, static tier: read-only checks against whatever the apps currently show (windows, composers, send controls, affordance counts, idle-stop state, readiness scan). Checks whose preconditions aren't met report SKIP with instructions, so the loop is run, follow the guidance, run again. A FAIL on `idle-stop` usually means the displayed conversation is mid-run, not breakage.
- **`tools/verify --nudge`** — adds reversible UI touches: paste probe text and confirm the send control enables, then revert via a focus-independent `AXValue` write; on Claude Code, expand one collapsed action bar and confirm the copy button mounts. The nudge tier refuses to run over a composer holding anything but a known placeholder (a select-all revert once ate a human draft) and re-verifies frontmost before every synthesized keystroke, bailing when the machine is in use.
- **`tools/verify --live claude|chatgpt|all`** — sends ONE probe message through the full production path (`send` → echo absorption → `waitForResponse` → `copyLastResponse`) in the app's *displayed* conversation, announcing the target and pausing three seconds first. Run it with throwaway conversations displayed; it proves the per-app lifecycle against a live response.
- **`ERROL_LIVE=1 swift test --filter Live`** — the **live** test category, integration tests that require both apps running (a plain `swift test` reports them as skipped, so the default suite stays side-effect-free). `LiveReadinessTests` is a read-only smoke: the sweep must find both sides Ready. `LiveRelayTests` is the actual-chat test — a real relay conversation through the production `runRelay` in fresh chats on both apps (seeding, framing, echo absorption, completion detection, copy, turn alternation, and the mutual sign-off if the models follow the rules), asserting at least two captured replies per side — the seed asks for a few exchanges before the sign-off so the steady-state verbatim-relay branch runs, not just the framed opening; the transcript lands in a temp file it names. It seizes focus and the clipboard for one to three minutes and costs a handful of real messages, so run it deliberately with hands off the keyboard; the draft, mid-run, and excluded-surface guards report as skips with instructions. The invoking process needs the Accessibility grant, like `ax-dump`.

After an app update breaks something: `swift test` says whether the pure contract moved, `tools/verify` names the first live check that fails, and `ax-dump`'s capture-and-diff finds the new tree shape to encode back into `Config.swift` — then the harness proves the fix.

Three build settings depart from the app template's defaults and matter: **App Sandbox is off** (a sandboxed app can neither get the Accessibility permission nor post keystrokes — with it on, Errol can do nothing), **`SWIFT_DEFAULT_ACTOR_ISOLATION` is `nonisolated`** (the engine runs on a worker thread while the main thread serves the panel; the template's main-actor default would fight that design), and **`LSUIElement` is set** (menu bar only, no Dock icon).

A markdown transcript of each run is written incrementally to `~/Documents/errol-transcript.md` (the app is launched from Finder with `/` as its working directory, so the path is absolute; macOS may ask once for access to the Documents folder).

## Setup

1. Open `app/Errol/Errol.xcodeproj` in Xcode and run, or build and copy `Errol.app` wherever you keep apps.
2. Launch both chat apps with a conversation open in each.
3. On a launch without the Accessibility grant, Errol opens an explainer window first: what the permission lets it do (read the two chat windows, type and send on the user's behalf, nothing leaving the Mac) and a button that triggers the system prompt — macOS only ever shows that dialog once per app, so later clicks deep-link to the Privacy & Security > Accessibility pane instead. The window polls for the grant and flips to a "Start Using Errol" button the moment it lands; dismissing it with Not Now is fine, since Start re-asks on demand.
4. Click the owl in the menu bar, type the instruction that should seed the conversation, and press Start. If the permission still isn't granted, Start triggers the prompt again; grant **Errol** in System Settings > Privacy & Security > Accessibility and press Start again. (When running from Xcode, the grant may attribute to Xcode instead — grant whichever the prompt names. Re-signed rebuilds can look like a new app to the privacy system; re-toggle the grant if pressing Start silently does nothing.)

The machine is effectively unusable while a run is active (shared clipboard and focus). Stop ends the run at the next safe point and keeps the transcript so far; when a run ends, focus is handed back to whatever was frontmost when Start was pressed.

## Controls

- **Readiness strip**: the top of the panel shows each side's live status — ChatGPT on the left, Claude on the right, the same sides the tiling uses. While the panel is open it re-scans every few seconds (paused during runs). The dot turns green with "Ready" when the app has a chat window with a composer — the same test the run preflight applies — "Not found" when it's running without a usable chat UI, and "Not running" when it isn't up. Claude showing only a Claude Code session reads Ready with "Code" as the surface, since the run would target it (see the window-scoping safeguard). Each side also names the surface it detected, reading the composer-level surface toggle first — ChatGPT's Chat/Work pair, Claude's Chat/Cowork tabs — because nothing else is trustworthy: ChatGPT's mode-switcher popup announces "ChatGPT" for both Chat and Work (it only distinguishes Codex mode, kept as the fallback), and Claude's two views share a URL. Claude falls back further to the window's claude.ai URL (chat, project chat, or a Claude Code session), with a note when other surfaces are open alongside. Where the window announces its active model, it appears after the surface, e.g. "Chat · Fable 5 · Extra" on Claude, "Work · 5.6 Sol High" on ChatGPT, or "Code · Fable 5 · Extra" on a Claude Code session. The scan never triggers the permission prompt (that stays tied to Start); without the Accessibility grant both sides show "No access".
- **Conversation**: a picker of canned shapes — Brainstorm, Debate, Code review, Adversary — each pairing purpose-specific pacing prose with a one-line topic field (its placeholder says what the shape expects: "What to brainstorm about", "The proposal to stress-test"). The opening message is the shape's body plus the topic, and **Edit full prompt** reveals exactly that text without changing the selected shape. A topic already entered appears after the template body; otherwise a visual “(add your topic or material here)” marks the same insertion point without becoming part of the prompt. The editor starts at eight lines, grows through thirteen, then scrolls. Choosing another shape while editing keeps the editor open and preserves each shape's in-progress draft; **Back to simple setup** is the explicit way back to its topic field. **Write from scratch** deliberately selects Custom and opens a blank full prompt. Templates remain starting text, not hidden framing — what the editor (or the composition) holds is the verbatim initial message handed to the first agent, wrapped in the framing preamble at send time, so it should read like an ordinary request, not an explanation of the relay. The shipped shapes live in `Core/Config.swift` (`defaultConversationTemplates`) with contract tests pinning that each references its topic, describes its own ending, and never duplicates the stop-sequence mechanics the standing rules own; the list itself — names, topic prompts, opening text, additions and deletions — is editable in **Settings**, and the picker reads the edited list.
- **Limit turns** (off by default): unchecked, a run ends when the conversation closes itself — the mutual sign-off (both sides sending the stop sequence), an empty reply, a response timeout, or the Stop button. Checked, the number field (default 10) also caps how many responses get relayed — extra protection, along with the message length cap, against two chatty models burning through usage limits.
- **Tile the chat windows side by side**: arrange ChatGPT left, Claude right before the run, so both conversations are visible. This sets window frames directly through AX (the same thing tiling utilities do) rather than driving the native Fill & Arrange menus, because the native cross-app "Left & Right" arrangement only pairs windows interactively and, in Claude Desktop, a menu-driven tile would act on whatever window is front — which can be a Claude Code session rather than the chat. `AXEnhancedUserInterface` (set as the Electron accessibility nudge) makes apps ignore or animate AX window moves, so it is temporarily dropped during each move. Tiling twice keeps the first snapshot, so restore always returns to the true original layout.
- **Inspect**: dump each app's windows, buttons, text inputs, and what the selectors match into the log — the first stop when a run misbehaves after an app update.
- Right-clicking the owl offers **Settings…** and **Quit**. Opening the transcript and restoring the pre-tiling window positions used to sit here too; both are gone from the menu, though the transcript is still written to the path above and `RelayController` still carries `openTranscript()` and `restoreWindows()` for the glass skin's own menu.
- **Settings** — the gear in the panel's title strip, or **Settings…** in the owl's right-click menu — opens the settings card: the wireframe idiom in a titled window that keeps the system close button and floats one level above the console (the same non-activating panel machinery, so it never steals focus from the chat apps). It manages the conversation shapes behind the picker: add new ones, rename them (names stay unique; **Custom** is reserved for the picker's write-from-scratch entry), edit the topic prompt and opening text, and delete — except the last shape, which the picker always needs. The list is stored wholesale in user defaults (`SettingsStore` in `Core/`) only while it differs from the shipped defaults, so an untouched list keeps tracking default-text improvements across updates; **RESET** appears on a shape that shares a name with a shipped default and has drifted from it. Editing the framing preamble was deliberately left out for now: that text carries the sign-off contract, and the substitution mechanism behind it (`{{stopSequence}}` in `RelayRules`, `Core/Relay.swift`) stays in place for when it returns.

Settings without UI — bundle IDs, timeouts, the stop sequence, the per-message length cap, selector keywords — live at the top of `Core/Config.swift`.

## Status and known brittleness

Verified against live trees and a completed 4-turn relay run (Aug 2026):

- **ChatGPT side (com.openai.codex, the unified app)**: the response's action bar uses a bare "Copy" button; "Copy message" (paired with "Edit message") belongs to the **user** message, and tables get "Copy table". The selector matches "copy" and excludes the qualified labels. An earlier reading that responses use "Copy message" was wrong and cost a debugging round: the relay kept copying its own pasted message back. A "Send" button and an `AXTextArea` composer are exposed. The app has a Chat/Work surface pair, switched by a top-center toggle rendered over AX as two `AXCheckBox` toggle buttons (`AXSubrole` "AXToggleButton", `AXValue` 1 on the active one, titles "Chat"/"Work") inside a group whose `AXDescription` is "Composer mode" (verified live, Aug 27 2026). Two traps around it: the "Switch mode, current mode:" popup does **not** track this toggle — it announces "ChatGPT" on both Chat and Work, so only Codex registers as a distinct mode there — and the composer placeholder is per-surface, "Message ChatGPT" vs "Work with ChatGPT" (an earlier reading called that label drift; `inputArea` matches by role, so only docs were affected). The composer's model pill is an `AXPopUpButton` whose *title* is "<model> <effort>" (e.g. "5.6 Sol High", verified on the Work surface) — but in Chat with the default model, the title is empty and the description reads "Select ChatGPT model" (title and description swap between the two states), so no model text exists over AX at all; Work always names the exact model and effort. In the default state the pill still *visually* renders the selected effort ("Medium"/"High"), but that text is unrecoverable over AX: the aria-label prunes the pill's subtree (zero AX children), the text-marker stream skips the pruned content (`AXStringForTextMarkerRange` over `AXTextMarkerRangeForUIElement` returns ""), and bounds-based markers are unsupported (probed live, Aug 2026) — so the strip reports "Default" and cannot do better. The strip finds the pill by effort-word suffix (`modelPopupSuffixes`) and reports the default state as "Default" via `modelPopupDefaultLabel`; an **empty** chat exposes no copy buttons at all, which looks like selector breakage but isn't. Neither app has a "copy last response" menu command. **Codex-mode fast-reply race** (root-caused live, Aug 27 2026): Codex-mode replies can complete in under 2 seconds — inside the old 4-second echo-absorption window. Since ChatGPT's echo can never move the count (its "Copy message" is excluded), the rise absorb saw was the *response*, which it folded into the baseline; the relay then waited forever on a count it could never exceed, and manually asking ChatGPT to repeat "fixed" it by mounting one more copy button. Echo absorption is now skipped on ChatGPT entirely (`echoCountsAsAffordance: false`), which also drops a needless 4-second stall per ChatGPT turn. The response's bare "Copy" was confirmed to mount without hover at completion in Codex mode, same as chat.
- **Claude side**: verified live — the composer is a "Write your prompt to Claude" `AXTextArea`, the send button matches "send", and per-message copy buttons match bare "copy" with the code/link/table excludes. On the chat surface an **empty** composer mounts no send button at all (captured Aug 27 2026, same as ChatGPT) — only Claude Code keeps a persistent, disabled send control; `confirmSend`'s button signal already only counts when a button existed at press time, so this costs nothing, but a send-button check is not a readiness signal on an idle chat. User messages expose copy buttons too (the echo absorption in step 1 exists for both apps). A Claude Code session window exposes "Prompt"/"Terminal input" inputs and its own Copy/Stop buttons; the exclusion markers correctly disqualify it while a chat window is open.
- **Claude Code as a fallback target** (verified live via `tools/ax-dump.swift`, Aug 27 2026, against a mid-turn session): composer is an `AXTextArea` labeled "Prompt", per-message copy buttons are bare "Copy" (the existing excludes fit), and a bare "Stop" button is present while a turn runs. **But the copy buttons are hover-gated**: each message's action bar (Copy, Rewind to here, Fork from here, Read aloud) stays unmounted behind a per-message "Show message actions" `AXButton` until a hover — or an `AXPress` on that toggle — expands it, and every conversation switch collapses all bars again (verified live with a seeded end-to-end probe, Aug 27 2026). An early dump showing bare "Copy" buttons on this surface had simply been hovered beforehand — a fresh response exposes only the toggle, which is why copy-button counting alone times out here. The toggle has exactly the mount timing detection needs: the echoed user message's toggle appears right after sending, the in-flight response contributes nothing while the Stop button shows, and the response's toggle mounts in the same beat the Stop button disappears. The relay therefore counts "message affordances" (mounted copy button or collapsed toggle — one per message, `messageActionsLabel` in `Core/Config.swift`) and expands the newest toggle via AXPress before copying. One trap: a "Send feedback" button matches the bare send keyword — `sendExcludeKeywords: ["feedback"]` exists solely to dodge it. Unused signal worth knowing: the sidebar's session buttons carry state as `AXTitle` prefixes ("Running …", "Idle …", "Awaiting input …"), a direct completion cross-check — but only while the sidebar is expanded: collapsing it removes those buttons from the tree entirely (the header button keeps just the bare session title, no state), leaving an "Open sidebar" button as the tell (and a way to restore the signal programmatically). Note the tree only carries the *displayed* conversation: a session running in the background contributes no Stop button and no transcript affordances. Verified idle from an independent shell (Aug 27 2026): the composer toolbar announces the session's model and effort as two **adjacent** `AXPopUpButton`s — a bare-titled model ("Fable 5") immediately followed by "Effort: Extra" — and the strip reads the pair via `effortPopupPrefix`: the effort match claims the popup visited just before it as the model, composing "Fable 5 · Extra". A "Usage: context N, plan N%" popup sits alongside, unused but worth knowing.
- **Chat vs Cowork vs Code** (verified live, Aug 27 2026): the Chat and Cowork views share one window, one URL (`claude.ai/new`), one composer label ("Write your prompt to Claude"), and one sidebar — none of those distinguish them, so the strip's URL-based surface naming cannot either. Note the current Claude Desktop build is single-window — there is no File > New Window, and Chat, Cowork, and Claude Code swap in place inside the one window via the world switcher — so the multi-window scoping story above describes an older build, and "no chat window open" is simply what the Code world always looks like. The real signals are two `AXRadioGroup` pairs, each with `AXValue` 1 on the active option: a top-level pair switching worlds (`AXDescription` "Chat and Cowork" vs "Code, …" — either label can append live session state, e.g. "Code, awaiting your input" and "Chat and Cowork, awaiting your input", so match the name before the comma) and a composer-level pair (`AXTitle` "Chat" vs "Cowork"). The top-level pair is what window exclusion reads; note that both options are always mounted, so `AXValue` is the only thing separating them and a label-only match would exclude every Claude window. Fallback markers if the radios move: a "Use incognito" button exists only in Chat, "Clear active" only in Cowork. The active model is readable on the Chat and Cowork surfaces from the `AXPopUpButton` whose `AXDescription` starts with "Model: " (e.g. "Model: Fable 5 · Extra"; Cowork showed "Model: Opus 5 · Extra"), name and effort level in one label; the readiness strip shows it next to the surface. Claude Code has no "Model:"-prefixed popup — it splits the announcement into the bare-model + "Effort:" popup pair covered in the fallback bullet above (a "Model:" popup observed on Code right after a surface switch was the chat composer still mounted mid-transition — re-dump after transitions before trusting a first observation); ChatGPT's model pill is covered in its own bullet. Caveat on self-observation: every agent-shell dump of the window hosting the agent's own session necessarily happens mid-turn, so that session's idle-state tree can never be captured from inside it.
- **Message numbering and list virtualization** (verified live, Aug 28 2026, from a relay run that hung): Claude renders each conversation message as an `AXGroup` (subrole `AXDocumentArticle`) named "Message N" — an absolute ordinal, user and assistant messages alike, delivered in `AXDescription` with an empty `AXTitle`. In long conversations the list is **virtualized**: only the last few messages stay mounted (the stuck window held "Message 6"–"Message 8" of 8; one of their "Message actions" toolbars was rendered 1px tall, half-clipped), so the affordance count falls as responses land and any count-above-baseline wait deadlocks. The newest message is always mounted, making the highest ordinal a monotonic completion signal (`lastMessageOrdinal`); the echo bumps it once and the response again, so completion is baseline+2 where echoes register. Verified on the Claude Code surface; whether the chat surface numbers messages the same way is unobserved — if it does not, chat falls back to the count and the streaming transition. Expanded action bars on this surface also put "Rewind to here" inside per-user-message toolbars, which is one of the `windowExcludeLabels` — that hover-dependent marker used to be the only thing classifying the window, and the world switcher now carries that job (see the window-scoping bullet above).
- The "Stop" label during streaming has not been observed live on either app's *chat* surface yet; on short conversations the echo-absorbed copy-button count detects completion there, and the virtualization hang has only been observed on the Claude Code surface so far — but nothing suggests the chat surfaces render unbounded lists, so assume long chat conversations need the ordinal or streaming-transition signal too. (Claude Code's running-state "Stop" button *has* been observed live — see above — so the streaming-transition backstop is real on that surface; on the chat surfaces it is unverified until streaming is captured there.)
- A run always seeds into whatever conversations are already open; opening a fresh chat on each side is the operator's job, deliberately, since Errol typing into the wrong conversation is worse than it starting in the last one. Beware "Continue in new chat" in ChatGPT, which carries prior context into the new conversation and leaves stale copy buttons in the tree — the affordance baseline then starts high, so open a genuinely fresh chat between runs.
- Surface detection for the readiness strip: ChatGPT's `Switch mode, current mode: <mode>` popup and Claude's `/epitaxy/` web-area URL (a Claude Code session) are verified against live trees (Aug 2026). The claude.ai path names for regular chats, new chats, and project chats in `surfacePathNames` are expected values that have not been observed yet — an unknown path shows up raw in the strip, which is the cue to add it to the map in `Core/Config.swift`.
- Selectors are label-based and will break when either app renames or icon-ifies its buttons after an update. Non-English UI needs the keywords in `AppSelectors` changed.
- OpenAI's app naming is mid-migration: the unified app can be named ChatGPT.app while identifying as `com.openai.codex`, with a "ChatGPT Classic.app" as `com.openai.chat`. `osascript -e 'id of app "ChatGPT"'` shows what this machine actually runs.

## Troubleshooting

- **App "not running" but it is**: bundle ID mismatch. Check with `osascript -e 'id of app "ChatGPT"'` and adjust the IDs in `Core/Config.swift`.
- **Empty tree / no buttons found in Inspect**: quit and relaunch Errol so the `AXManualAccessibility` nudge reapplies; confirm with `swift tools/ax-dump.swift <app> --buttons`.
- **Wrong button pressed (e.g. "Copy code")**: adjust `copyExcludeKeywords` in `Core/Config.swift`.
- **Paste lands but Return doesn't send**: some layouts use Cmd+Return; change `keystroke(keyReturn)` to `keystroke(keyReturn, flags: .maskCommand)` in `send(_:to:)`.
- **Start silently does nothing after a rebuild**: the privacy system treats a re-signed build as a new app; re-toggle Errol (or Xcode, for Xcode-launched runs) in System Settings > Privacy & Security > Accessibility.
