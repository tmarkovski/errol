# How Errol works

The engineering notes behind Errol: how the relay drives the two apps, the safeguards that keep it from typing into the wrong place, how the code is laid out and tested, and what has been observed about each app's accessibility tree. For what Errol is and how to install it, see the [README](../README.md). Paths below are relative to the repository root.

Errol relays a conversation between the ChatGPT app (the unified ChatGPT and Codex app) and Claude Desktop on macOS by automating their UIs: it presses each app's "Copy" button and pastes the response into the other app's composer, exactly like a human relaying messages between two chat windows.

It is a menu bar app: the Errol symbol sits in the status bar, and clicking it opens a floating panel where you type the instruction that seeds the conversation into the composer and press **Start relay**. There is no CLI; **Inspect Apps**, in a debug build's right-click menu on the icon, covers the selector debugging the old command-line flags used to.

## What we're building and why

An experiment in having two AI assistants talk to each other **as products**, not as raw models. Going through the desktop apps means each side keeps its own system prompt, tools, memory, and subscription context. There are no APIs or SDKs involved anywhere; the entire mechanism is the macOS Accessibility API (`AXUIElement`) plus the system clipboard and synthesized keystrokes.

**Design decision: the desktop apps are the point, not a workaround.** A CLI-to-CLI version (`claude -p` piped into `codex exec` in a loop) was considered and rejected. It would be simpler (no permissions, no clipboard, no focus stealing), but it talks to the bare models. This project specifically wants each side operating inside its app: Claude Desktop with its projects, connected tools/MCP servers, memory, and settings; Codex with its threads, skills, and workspace context. The UI relay is the only way to get that, so the added fragility is accepted. Do not "simplify" this into a CLI pipeline.

## How it works

The conversation is framed for both participants before the relay goes hands-off. The first agent receives the ground rules (this is an agent-to-agent conversation, the human is not participating, and it can sign off by including the stop sequence, default `[[END-CONVERSATION]]`) followed by the instruction typed into the panel. The rules also push back on the single-shot habit — treat this as a multi-turn dialogue, contribute incrementally, and never *initiate* the sign-off in a first reply ("initiate" so that reciprocating a peer's early sign-off stays allowed) — because in early live runs both models would answer the seed completely in one message and immediately sign off, especially on brainstorm-shaped tasks. Pacing beyond that baseline belongs in the instruction text, where it stays visible and editable per run — the panel's conversation shapes carry purpose-specific pacing (a brainstorm demands rounds of divergence before converging), and the live relay test's seed demands three replies per side. When the first response comes back, the second agent receives the same rules plus both the initial message and that response, so both sides start from identical context. Every message after those two framing messages passes through verbatim. Ending is a handshake: a reply containing the stop sequence is still relayed, so the peer sees the goodbye and can answer with its own — the run closes when two consecutive replies carry the marker (the rules tell each agent to reply to a sign-off with one of theirs). An empty reply ends the run immediately, since there is nothing to relay. A run set to end when you stop it drops the sign-off paragraph from the rules for one saying the human will end the conversation (`RelayRules.humanEnds`), and the loop ignores the marker, so only Stop ends that run on purpose. Each perch's subline shows its part in the run — "Replying…", "Reply ready", "Waiting", or "Signed off" (only a real sign-off leaves that showing after a run).

One turn of the loop:

1. Wait until the current speaker finishes its response. Completion is detected when **no "Stop" button** is visible (still streaming), any of three signals says a response landed, and that state holds for two consecutive polls. The signals, in order of precision: a **new per-message affordance** beyond the baseline (an affordance is a mounted copy button *or* — on Claude Code, where the action bar stays unmounted until hovered — the collapsed "Show message actions" toggle standing in for it; each rendered message carries exactly one of the two, so the count is a message count); the newest message's **ordinal** advancing far enough past the baseline to be the response — Claude names every message "Message N", and the newest is always mounted; and the **streaming transition** — the Stop button was observed and has gone, so the response it belonged to is complete whatever the counters claim. Three signals because the count alone hung a real run (Aug 28 2026): Claude **virtualizes** long conversations, unmounting older messages as new ones land, so the affordance count plateaus or falls — the stuck run's baseline was 7 with the finished response on screen and only 3 affordances mounted, a threshold no response could ever cross. The ordinal survives virtualization but only exists where messages are numbered; the streaming transition is the app-agnostic backstop for everything else. On Claude, the just-pasted user message grows a counted affordance of its own, so right after sending, the relay waits for that echo and folds it into the baseline; only affordances beyond it can belong to the response. On ChatGPT the echo mounts "Copy message", which the copy selector excludes — nothing to absorb, and the wait is skipped (`echoCountsAsAffordance`): waiting there would misread any response that completes inside the wait window as the echo and fold it into the baseline, leaving the relay waiting forever (the Codex-mode fast-reply race below).
2. Bring the speaking app frontmost, then press the last copy button in the tree (newest message) and confirm the press landed by watching `NSPasteboard.changeCount`. When the newest affordance is the collapsed toggle instead, press it first and wait for the bar's copy button to mount — the AXPress equivalent of the hover that normally expands it. The activation matters as much as it does before typing: the button's handler writes the clipboard from the app's renderer, and Chromium refuses that write while the document is unfocused, so an unfocused press reports success and copies nothing (it killed a run on Aug 31 2026 — the operator had clicked away mid-turn). A miss is retried once behind a LaunchServices activation, the call that moves key status too; only then does the run stop.
3. Bring the other app frontmost and verify it actually got there (see safeguards), focus its composer (`AXTextArea`), synthesize Cmd+V, wait for the paste to render, press the send button.
4. Swap speaker and listener. Repeat until both sides sign off (or the optional turn cap).

Both apps are Chromium-based, and Chromium exposes an empty accessibility tree until nudged, so `AXManualAccessibility` is set on both at the start of each run. Everything runs against label-based selectors, kept per app in `AppSelectors` structs inside `Config` because they are the part most likely to break. The labels differ between the apps: ChatGPT calls per-message copies "Copy message" (bare "Copy" is code blocks, "Copy table" is tables), while Claude uses "Copy" with excludes.

Safeguards discovered the hard way:

- **Verified activation.** From a background process under macOS cooperative activation, `NSRunningApplication.activate` returns true without effect and setting the AX `kAXFrontmostAttribute` returns success without effect; LaunchServices (`/usr/bin/open -b`) is what actually brings an app forward. Synthesized keystrokes go to the frontmost app regardless of AX focus, so the relay confirms the target is frontmost before typing — via the system-wide AX focused application, falling back to the window server's front window when the focused app's AX server won't answer (Electron apps go quiet intermittently) — and refuses to send keystrokes otherwise. Without this, the seed gets typed into whatever window the user last touched.

- **Verified paste.** Frontmost isn't enough for typing: synthesized keystrokes follow the *key window*, which can stay behind on another window (Errol's own non-activating panel among them) while the target app reads as active — the paste then lands nowhere and the relay presses Send on an empty composer (observed live, Aug 27 2026). After pasting, `send` waits for either the payload text in the composer or a newly mounted, composer-scoped pasted-text attachment chip. The second signal matters because ChatGPT turns long pastes into `pasted-text.txt` while leaving the text area's AX value at its placeholder; treating that as a miss pasted the same attachment twice (observed live, Aug 30 2026). Claude has the same behavior with an empty text value: its preview is labeled “Pasted text, pasted, N lines” and its remove button “Remove Pasted text, pasted, N lines” (observed live, Sep 7 2026). The Claude attachment row is under the input’s third parent, while ChatGPT’s is under its immediate parent; each app’s selector specifies that composer scope so historical attachments cannot confirm a paste. Only when neither signal appears does Errol force a LaunchServices activation (the one call that also moves key status) and paste once more before warning.

- **Bound windows.** At connection, each side is bound to its app's window, the one the human chose where the app has several, and every operation checks that window again — before the capture and delivery gates, once more after taking them, immediately before every paste and submit keystroke, and on every poll of the response wait. A window that is minimized, or behind another of the app's windows when a keystroke is due, holds the run rather than typing blind: "Paused: Claude's window isn't showing … Bring it back to continue, or Stop." Nothing is copied, pasted, or activated while held; the wait's inactivity clock stops, its baseline is kept, and the run resumes on its own when the window is back. What the window shows is not compared: the connection is the window, and a conversation switched inside it is written into all the same. The log's `targeting` line names what the window showed when it was connected — its route where the surface exposes one (`/chat/<uuid>` on a Claude chat, `/epitaxy/<id>` on a Claude Code session), else its title. An app that quits or a window that closes ends the run instead, with that as the reason (`Core/Destination.swift`).

- **Covered conversations.** A modal dialog over a side's conversation, such as Claude's image viewer, takes everything behind it out of the accessibility tree: the composer, the copy buttons, the "Message N" groups, and the Stop button (captured live, Sep 25 2026: about 870 elements down to 66, `claude-code-image-viewer`). Read as it stands, that tree is a reply that just finished with nothing to copy. A run on Sep 24 2026 ended on exactly that, "Couldn't copy Claude's reply", with Claude still streaming behind the viewer. A window whose composer is gone while a dialog is in it (an `AXGroup` with subrole `AXApplicationDialog` or `AXApplicationAlertDialog`) counts as covered (`coveringDialog` in `Core/Elements.swift`). A dialog over a conversation that stays readable, such as a popover, doesn't count. A covered side holds the run the way a hidden window does: the response wait stops observing and its inactivity clock stops, the copy and the paste are held, and a start is refused. The console shows the same full-width alert as an app that won't come forward, asking for the dialog to be closed by its name ("Please close “Image preview” in Claude to continue"). Errol never closes the dialog itself. A copy that finds nothing looks for a dialog once more before the run ends on it, because one live check caught the conversation gone before the dialog was in the tree.

- **Unsent work stays unsent.** Before a paste — at Run for both sides, and at every delivery — the composer about to be pasted into is read: text past the app's placeholder is a draft, a mounted pasted-text chip is an attachment, a visible Stop control is a reply underway, and a value that cannot be read establishes nothing. Any of them holds the run ("Paused: Claude has an unsent draft") until the human finishes or clears it, or refuses the start with the same reason under the composer. Only Errol's own paste is exempt, and only inside the send that made it: a retry is made over a composer that stands exactly as it did before the keystroke, never over one that took something.

- **The clipboard is the human's.** Each copy and each delivery takes a lease on the pasteboard (`Core/ClipboardLease.swift`): what was there — every item and representation — is captured before the operation writes, and put back the moment the reply is in memory or the send is over, but only if the clipboard still holds the operation's own write. A copy the human made in between stays, and is never pasted as the relay's message either: the payload is checked to be on the clipboard immediately before each Cmd+V, and a send that finds it gone is withheld and retried from the gate. A capture that cannot be read whole is left alone rather than restored in part.

- **Window scoping.** All searches run inside one chosen chat window per app, re-resolved on every poll. Claude Desktop can host Claude Code sessions whose windows contain their own "Copy" and "Stop" buttons — including, if you develop this tool inside one, the session driving the relay. A window is classified by Claude's own world switcher: the top-level `AXRadioGroup` whose selected option names the mounted world, and a window showing "Code" is never chosen while any chat window exists (`excludedWorldName` in `Core/Config.swift`; the option appends live session state after a comma, e.g. "Code, awaiting your input", so only the name before it is matched). Marker labels ("Terminal input", "New terminal", "Rewind to here") remain as a backstop for builds with no switcher, ORed with it — an unrecognized Code session gets relayed into, while a wrongly excluded chat window only reports the wrong surface, so the two signals are combined in the direction that adds exclusions. When Claude Desktop has *no* chat window, a Claude Code session window with a composer is a deliberate fallback target (`excludedSurfaceIsFallback` in `Core/Config.swift`): the strip reports it Ready as "Code" and the preflight logs a NOTE naming what it will type into. That weakens the original never-touch-Claude-Code guarantee by choice — if the only session open is the one developing Errol, the relay will land in it, so leave the world switcher on Chat (or turn the fallback off) while developing. On the current single-window build that is the only way to have a chat window at all, which also means the NOTE fires on every run started from the Code world; it reports which world is being typed into, not a fault. The preflight still refuses when an app has no targetable window at all.
- **Send confirmation.** Sending prefers pressing the app's send button over a Return keystroke, then confirms the message actually left, escalating through Return and Cmd+Return before warning. Confirmation accepts either of two signals: the composer's value moved off the payload, or the send control dropped back to its empty-composer state — disabled on Claude Code, where the Send button is a persistent icon button (`AXDescription` "Send", disabled while the composer is empty), unmounted entirely on ChatGPT. The composer value alone is not trusted because it has been observed reading stale for seconds after a successful send on Claude Code (Aug 27 2026), which sent the old single-signal check through the whole keystroke escalation on a message that was already gone.

## Layout

Everything lives in the Xcode project at `app/Errol` (`Errol.xcodeproj`). Inside the app target:

- `ErrolApp.swift`: the `@main` entry point; a placeholder Settings scene plus the delegate adaptor that installs the shell.
- `MenuBarController.swift`: the AppKit shell — the status item and the floating panel hosting the SwiftUI view. It stays AppKit because the panel must be a non-activating floating panel (the Spotlight pattern): SwiftUI's `MenuBarExtra` window dismisses itself whenever another app activates, which the relay does on every turn, so the controls would vanish exactly when a run needs them visible.
- `RelayController.swift`: the observable model behind the panel — form state, the log, the steering field, and the start/stop/inspect wiring. It drives the apps only through `RelayEngine.swift`: the seam that owns the permission, the readiness sweeps, and the run's worker thread, reporting back over the engine's event stream. The app runs `LiveRelayEngine`; the SwiftUI previews (`Perch/PerchPreviews.swift`) run `PerchPreviewEngine`, which plays a run — turns, holds, steering notes and their receipts — on a clock of seconds without touching either app, so the canvases' Start, Stop, and Pause to steer change state as in the app and relay nothing.
- `Core/`: the relay engine, split by concern. `Config.swift` holds bundle IDs, label keywords, caps, and timings; `Accessibility.swift` and `Elements.swift` the AX wrappers and window-scoped element finders; `ElementNode.swift` the protocol the finders are generic over, with live-AX and recorded-fixture conformances; `Activation.swift` the verified-activation logic; `Arrangement.swift` the window tiling; `Keyboard.swift` the synthesized keystrokes; `RelayActions.swift` the copy/send/wait primitives; `Relay.swift` the message framing and the orchestration loop; `Inspect.swift` the selector-debugging dump; `Readiness.swift` the continuous scan behind the panel's readiness strip; `Logging.swift` the log, the per-run debug log, and the cancellation flag behind Stop.

Repo-level tooling lives in `tools/`: `ax-dump.swift` is a standalone inspector (`swift tools/ax-dump.swift claude --buttons`) that dumps the live accessibility tree of any running app from any shell holding its own Accessibility grant — no Xcode, no build step, and Errol doesn't need to be running. Its header comment documents the modes (summary fingerprint, full tree, button census, per-element attribute dump, menu bar, fixture-JSON capture) and the capture-and-diff workflow for developing detection heuristics.

## Testing

The detection contract is testable at several cost levels, and all of them run the production code — `Package.swift` builds the same `Core/` sources the app compiles (pointed at in place, no copies) as the **ErrolKit** library, which the test suite and the harness link. The Xcode app does not depend on the package and builds exactly as before; the package exists so the tools cannot drift from the app. Tools and tests reach ErrolKit's internals via `@testable import` (debug builds enable testability), so Core carries no public-API annotations for their benefit.

- **`swift test`** — contract tests, no apps needed, in two layers. The selector layer pins the pure label logic: copy-selector semantics per app (including the "Copy message" echo asymmetry that caused the Codex fast-reply race), the `echoCountsAsAffordance` flags, the send-button "feedback" trap, announcement parsing, surface-name precedence, and the relay's message framing, length cap, and stop-sequence contract. The scenario layer runs the *finders themselves* over recorded trees: the walk is generic over the `ElementNode` protocol (`Core/ElementNode.swift`), with live `AXUIElement`s and JSON fixtures as its two faces, so `tests/ErrolKitTests/Fixtures/` drives the identical detection code the relay runs. One fixture per screen the detection must classify — ChatGPT Chat/Work home (new chat) and open conversations (plugging into an existing chat), Codex mode, mid-stream; Claude Chat/Cowork home and conversations, a project chat, Claude Code with action bars collapsed and expanded, sidebar collapsed and expanded, streaming, and the old multi-window layout — each asserting the full verdict: chosen window, exclusion, surface, model, affordance count and order, send/stop/composer. Run these on every selector change. `ERROL_TEST_LOG=1 swift test` (off by default) dumps every scenario's tree shape, per-window classification, and detection outcome to stderr for debugging a failure.
- **`tools/ax-dump.swift <app> --capture`** — records the live windows' trees as fixture JSON. When an app update moves a tree, recapture the affected screens into `tests/ErrolKitTests/Fixtures/` and the scenario tests check the new shape against the whole contract. Four fixtures are real captures with sidebar conversation titles, project names, message text, and the account name anonymized — structure, roles, and counts untouched: the two home screens (`chatgpt-chat-home`, `claude-chat-home`, Aug 27 2026), `claude-virtualized-conversation` (Aug 28 2026), the exact window of the stuck-relay bug — a long Claude Code conversation with only the last three of eight messages mounted, captured while the undetected response and sign-off were on screen — and `claude-code-image-viewer` (Sep 25 2026), a Claude Code session with an image open in Claude's viewer, which hides the whole conversation (see Covered conversations above). The remaining fixtures are synthesized from the live-verified shapes in the field notes below — replace them with real captures as screens get re-observed.
- **`tools/verify`** — the guided live harness, static tier: read-only checks against whatever the apps currently show (windows, composers, send controls, affordance counts, idle-stop state, readiness scan). Checks whose preconditions aren't met report SKIP with instructions, so the loop is run, follow the guidance, run again. A FAIL on `idle-stop` usually means the displayed conversation is mid-run, not breakage.
- **`tools/verify --nudge`** — adds reversible UI touches: paste probe text and confirm the send control enables, then revert via a focus-independent `AXValue` write; on Claude Code, expand one collapsed action bar and confirm the copy button mounts. The nudge tier refuses to run over a composer holding anything but a known placeholder (a select-all revert once ate a human draft) and re-verifies frontmost before every synthesized keystroke, bailing when the machine is in use.
- **`tools/verify --live claude|chatgpt|all`** — sends ONE probe message through the full production path (`send` → echo absorption → `waitForResponse` → `copyLastResponse`) in the app's *displayed* conversation, announcing the target and pausing three seconds first. Run it with throwaway conversations displayed; it proves the per-app lifecycle against a live response.
- **`ERROL_LIVE=1 swift test --filter Live`** — the **live** test category, integration tests that require both apps running (a plain `swift test` reports them as skipped, so the default suite stays side-effect-free). `LiveReadinessTests` is a read-only smoke: the sweep must find both sides Ready. `LiveRelayTests` is the actual-chat test — a real relay conversation through the production `runRelay` in fresh chats on both apps (seeding, framing, echo absorption, completion detection, copy, turn alternation, and the mutual sign-off if the models follow the rules), asserting at least two captured replies per side — the seed asks for a few exchanges before the sign-off so the steady-state verbatim-relay branch runs, not just the framed opening. It seizes focus and the clipboard for one to three minutes and costs a handful of real messages, so run it deliberately with hands off the keyboard; the draft, mid-run, and excluded-surface guards report as skips with instructions. The invoking process needs the Accessibility grant, like `ax-dump`.

After an app update breaks something: `swift test` says whether the pure contract moved, `tools/verify` names the first live check that fails, and `ax-dump`'s capture-and-diff finds the new tree shape to encode back into `Config.swift` — then the harness proves the fix.

Exclusion now reads Claude's world switcher — `excludedWorldName` in `Core/Config.swift` against the selected option of the top-level `AXRadioGroup` — so it asks the app which world is mounted instead of inferring it from furniture. The furniture labels stay as the backstop for the switcher-less multi-window build, ORed rather than overruled: missing a Code session means relaying into it, while a spurious exclusion only mislabels the surface. `ClaudeCodeScenarioTests.testClassificationSurvivesTheHoverState` pins the three Code fixtures to one verdict.

- Each of the completion fix's new signals has an unverified half: "Message N" numbering is confirmed on the Claude Code surface only (the chat and Cowork surfaces may or may not number messages), and the Stop-button streaming transition is confirmed on Claude Code only (neither app's chat surface has been dumped mid-stream). A long conversation on a chat surface exercises both — capture one streaming and one virtualized chat state when the chance comes. Capturing those means displaying each state and running `--capture` — and the Claude Code idle state needs an independent shell, since a session cannot dump its own window idle (see the field notes).
- Small ergonomics: `nudge-expand` SKIPs when the newest message's bar is already expanded (switching conversations collapses all bars and re-arms it), and the static tier reports 0 affordances on a ChatGPT home screen — both are precondition SKIPs, not failures, but the guidance could name the fix more directly.

Three build settings depart from the app template's defaults and matter: **App Sandbox is off** (a sandboxed app can neither get the Accessibility permission nor post keystrokes — with it on, Errol can do nothing), **`SWIFT_DEFAULT_ACTOR_ISOLATION` is `nonisolated`** (the engine runs on a worker thread while the main thread serves the panel; the template's main-actor default would fight that design), and **`LSUIElement` is set** (menu bar only, no Dock icon).

Errol keeps an in-memory conversation summary until **New topic in these chats**. Full replies stay in the chat apps. Debug logs persist under `~/Library/Logs/Errol/`.

## Setup

For guided checks against the installed desktop apps, run
`tools/verify --guided --suite desktop-smoke`. The harness walks through Chat,
Work, Codex, Claude Chat, Cowork, and Code with disposable conversations and
records delivery evidence. See [Live desktop compatibility tests](desktop-verification.md)
for the full scenario matrix, prerequisites, reports, and verification limits.

1. Open `app/Errol/Errol.xcodeproj` in Xcode and run, or build and copy `Errol.app` wherever you keep apps.
2. On a launch without the Accessibility grant, Errol opens its main panel with the permission request in the console's place: the same capsule, with the request at one end and **Open System Settings** at the other, the console's own button. The button opens the list in Privacy & Security, which macOS 27 calls Device Control and Data Access and earlier versions call Accessibility, and docks a small panel under the System Settings window holding Errol's icon, the way Codex Computer Use asks for the same grant. Dragging the icon into the list adds Errol and allows it; there is no system prompt (the `PermissionGuide/` folder, whose code is adapted from [PermissionFlow](https://github.com/jaywcjlove/PermissionFlow) and follows the Settings window without needing any permission itself). If Errol is already in the list but switched off, turning it on works too. The screen names whichever list this Mac has (`Core/AccessPermission.swift`). The panel checks for access every second and crossfades to setup when macOS confirms the grant, putting the guide away and bringing the console forward; hiding and reopening the panel does not skip it, and revoking access brings it back. (When running from Xcode, the grant may attribute to Xcode instead; if dragging Errol in doesn't clear the screen, turn on Xcode as well. Re-signed rebuilds can look like a new app to the privacy system; re-toggle the grant if nothing responds.)
3. Click the Errol icon in the menu bar. Use **Open ChatGPT**, **Open Claude**, or **Open both apps** if needed. A single eligible window connects automatically. Claude keeps to one window, but ChatGPT can open more with File > New Window; when an app has several, its line under the editor asks you to choose one and lists them by title. Once connected, the line shows the window's mode, then its model with the effort a shade lighter. A connection follows that window, including a different conversation subsequently displayed inside it.
4. Type the topic, set who starts and how the relay ends in the row above it, then press **Start relay**. Clicking **ChatGPT starts** hands the first turn to Claude, and clicking it again hands it back; the ending is a menu. The Windows menu applies an arrangement immediately. Start stays unavailable while a destination needs attention or the topic is empty, with the reason beside it.

The machine is effectively unusable while a run is active (shared clipboard and focus), and typing into either chat app mid-run breaks the relay. **Stop** ends the run at the next safe point; when a run ends, the console takes the keyboard back from the chat app that replied last, and the two next intentions stand beside the summary: **Another topic here** keeps the connections (both are verified again before Send comes back), and **Set up fresh conversations…** returns to the connect steps so new chats can be opened in the apps and connected. Minimizing a connected window, or leaving a draft in a composer, does not break the run: it holds with the reason in the capsule ("Paused: Claude's window isn't showing", "Paused: ChatGPT has an unsent draft") and resumes on its own once the window is back or the composer is clear — see the safeguards above. Switching conversations inside a connected window is not a hold: Errol writes into whatever that window shows. Every copy, paste, and send goes to the window that was connected, never to another window the app happens to have in front.

## Controls

The console is **Perch** (`app/Errol/Errol/Perch/`), implementing the [console layout proposal](design-proposals/console-layout/README.md). It keeps the 860 × 156 capsule, two participants at the ends, and a separate summary beneath it.

- **Participants and destinations:** stable app names and badges distinguish ready, attention, replying, and waiting. Click an icon to focus its app, with the connected window in front, or to open the app while it is closed. Rest the pointer on an icon for its tip: what a click does, then the window's mode, model, effort, and status. The line under the box shows each side's mode, model, and effort, with no chevron; nothing is said about the conversation in the window, since whether it is new can't be told reliably. When the app has several windows, click the line to choose one; while the app is closed, click it to open the app. During a run it is only a label. A connection not checked since the last run stays muted and its status reads **Last used**.
- **Session options:** before a run, the top row names who starts, how the run ends, and the window arrangement. Who starts is a choice of two, so a click swaps it, with no menu; swap arrows stand where the other chips' chevrons are. A run ends **when both agree** (the mutual sign-off), **after a set number of turns**, or **when you stop it**.
  - With a turn limit, a stepper beside the chip sets the count, from 1 to 99. The limit is a maximum: a mutual sign-off can end the relay sooner.
  - A run set to end when you stop it has no sign-off. The assistants' rules say the human will end the conversation, a stray end marker is relayed like any other text, and the run goes on until you press **Stop**. An empty reply, a timeout, or a failure still ends it. Mind the usage limits, since nothing caps the replies.
  - On a narrow display, who starts and the arrangement are grouped under **Run options**, where who starts is one command that swaps it. During and after a run, this row shows the topic instead.
- **Running and steering:** a recessed status panel says who is replying or what is being sent, with the turn, elapsed time, and note receipt. **Pause to steer** waits for any active copy or delivery before opening the note editor. Return sends the note and continues; with an empty note it resumes. Escape clears a note, or resumes if already empty. **Stop** remains available. A queued note shows its next destination and **Clear note**. Recovery and completion messages preserve the relay's actual outcome; only mutual completion gets a success check. Once the run is over, the panel says how it ended and little else: a note shows there only if it never went, since the summary already lists the ones that did. For the whole run, paused included, the menu-bar icon is lit the way macOS lights the microphone indicator: the mark turns white on a capsule of the theme's accent that fills the item. It goes back to the plain mark when the run ends.
- **Conversation summary:** the window beneath the console has a reply count, joined by the run's time once it is over ("9 replies in 1:21"), and survives pause/resume with its scroll position intact. Model summaries are plain text; original excerpts are quoted and italicized. Attempted notes retain their Sending, Sent, Unconfirmed, or Not sent receipt. Hover or keyboard-focus a row while paused or finished to **Show ChatGPT window** or **Show Claude window**; this shows the connected window, without navigating to a historical reply.
- **Focus and availability:** a side's tip shows throughout a run without activating another app. Focusing an app from its icon, like **Show window**, requires an acknowledged pause while running, and the tip says so ("Pause to focus"). **Show window** preserves the note and returns keyboard focus to it; the icon leaves the keyboard with the app it focused. Resume waits for that window action to finish. Destination changes, arranging/restoring windows, Inspect Apps, Finder, and updates are unavailable during a run. The focus alert still covers the console when an app needs to be brought forward, or when a dialog such as Claude's image viewer covers a side's conversation.
- **Windows:** the Windows menu offers Side by side, Stacked, Fill screen, and Keep positions. Moving layouts apply immediately to connected windows. **Restore Window Positions** only restores windows still at their arranged positions; it leaves windows moved by hand alone. Restoration is never automatic at run end.
- **App menu:** the persistent **···** button and the menu-bar icon's right-click menu share About Errol, Check for Updates, the Appearance and Color Palette choices, the logs, and Quit; a debug build adds Inspect Apps. There is no settings screen: appearance changes apply immediately from the menu. About Errol opens a small window of its own with the icon, version, website, the third-party licenses (`THIRD_PARTY_NOTICES.txt`), and the copyright.
- **Closing:** drag the capsule's bare surface to move it. Click the menu-bar icon, use Escape on the console, or press ⌘W to put it away. Quit ends the process. The summary follows the console; transfer animations remain enabled and the waiting-window veils are currently disabled.
- **Debugging:** Show Last Run Log opens a floating window with the current run's in-memory log. Show Debug Logs in Finder reveals the latest file under `~/Library/Logs/Errol/` (the last twenty runs are kept). Inspect Apps, in a debug build, dumps detected windows, controls, and selector matches into that log. Failed paste verification also records diagnostic snapshots alongside the log.

To render the actual views without touching the installed app, run `tools/console-preview/render /tmp/errol-preview`; add `--dark` for dark appearance. It uses the preview engine and sends no messages. The renderer also checks pause and window-action behavior. In Xcode, `Perch/PerchPreviews.swift` has a canvas for each of the console's states, before, during, and after a run, standing as the panel does; `render /tmp/errol-preview canvas` draws the same states.
Settings without UI — bundle IDs, timeouts, the stop sequence, the per-message length cap, selector keywords — live at the top of `Core/Config.swift`.

## Status and known brittleness

Verified against live trees and a completed 4-turn relay run (Aug 2026):

- **ChatGPT side (com.openai.codex, the unified app)**: the response's action bar uses a bare "Copy" button; "Copy message" (paired with "Edit message") belongs to the **user** message, and tables get "Copy table". The selector matches "copy" and excludes the qualified labels. An earlier reading that responses use "Copy message" was wrong and cost a debugging round: the relay kept copying its own pasted message back. A "Send" button and an `AXTextArea` composer are exposed. The app has a Chat/Work surface pair, switched by a top-center toggle rendered over AX as two `AXCheckBox` toggle buttons (`AXSubrole` "AXToggleButton", `AXValue` 1 on the active one, titles "Chat"/"Work") inside a group whose `AXDescription` is "Composer mode" (verified live, Aug 27 2026). Two traps around it: the "Switch mode, current mode:" popup does **not** track this toggle — it announces "ChatGPT" on both Chat and Work, so only Codex registers as a distinct mode there — and the composer placeholder is per-surface, "Message ChatGPT" vs "Work with ChatGPT" (an earlier reading called that label drift; `inputArea` matches by role, so only docs were affected). The composer's model pill is an `AXPopUpButton` whose *title* is "<model> <effort>" (e.g. "5.6 Sol High", verified on the Work surface) — but in Chat with the default model, the title is empty and the description reads "Select ChatGPT model" (title and description swap between the two states), so no model text exists over AX at all; Work always names the exact model and effort. In the default state the pill still *visually* renders the selected effort ("Medium"/"High"), but that text is unrecoverable over AX: the aria-label prunes the pill's subtree (zero AX children), the text-marker stream skips the pruned content (`AXStringForTextMarkerRange` over `AXTextMarkerRangeForUIElement` returns ""), and bounds-based markers are unsupported (probed live, Aug 2026) — so the strip reports "Default" and cannot do better. The strip finds the pill by effort-word suffix (`modelPopupSuffixes`) and reports the default state as "Default" via `modelPopupDefaultLabel`; an **empty** chat exposes no copy buttons at all, which looks like selector breakage but isn't. Neither app has a "copy last response" menu command. **Codex-mode fast-reply race** (root-caused live, Aug 27 2026): Codex-mode replies can complete in under 2 seconds — inside the old 4-second echo-absorption window. Since ChatGPT's echo can never move the count (its "Copy message" is excluded), the rise absorb saw was the *response*, which it folded into the baseline; the relay then waited forever on a count it could never exceed, and manually asking ChatGPT to repeat "fixed" it by mounting one more copy button. Echo absorption is now skipped on ChatGPT entirely (`echoCountsAsAffordance: false`), which also drops a needless 4-second stall per ChatGPT turn. The response's bare "Copy" was confirmed to mount without hover at completion in Codex mode, same as chat. **The composer rewrites pastes** (observed live Sep 8 2026): a pasted markdown fence becomes a rendered code block — an `AXCodeStyleGroup` with a "Code language" popup — and the fence line, language tag included, is gone from the text area's AXValue; quote characters are swapped on the way in too. That is why the paste receipt matches on letters and digits with fence lines skipped (`pasteNeedle` in `Core/RelayActions.swift`), falls back to the composer growing by a third of the payload, and never pastes again into a composer that has moved (`pasteRetryIsSafe`): the double paste of Sep 8 2026 was the old first-line needle, `"```text"`, failing on a reply that opened with a fence, and the retry landing on top of the paste that had arrived. The composer captured after that paste is `tests/ErrolKitTests/Fixtures/chatgpt-work-composer-fenced-paste.json`.
- **Claude side**: verified live — the composer is a "Write your prompt to Claude" `AXTextArea`, the send button matches "send", and per-message copy buttons match bare "copy" with the code/link/table excludes. On the chat surface an **empty** composer mounts no send button at all (captured Aug 27 2026, same as ChatGPT) — only Claude Code keeps a persistent, disabled send control; `confirmSend`'s button signal already only counts when a button existed at press time, so this costs nothing, but a send-button check is not a readiness signal on an idle chat. User messages expose copy buttons too (the echo absorption in step 1 exists for both apps). A Claude Code session window exposes "Prompt"/"Terminal input" inputs and its own Copy/Stop buttons; the exclusion markers correctly disqualify it while a chat window is open.
- **Claude Code as a fallback target** (verified live via `tools/ax-dump.swift`, Aug 27 2026, against a mid-turn session): composer is an `AXTextArea` labeled "Prompt", per-message copy buttons are bare "Copy" (the existing excludes fit), and a bare "Stop" button is present while a turn runs. **But the copy buttons are hover-gated**: each message's action bar (Copy, Rewind to here, Fork from here, Read aloud) stays unmounted behind a per-message "Show message actions" `AXButton` until a hover — or an `AXPress` on that toggle — expands it, and every conversation switch collapses all bars again (verified live with a seeded end-to-end probe, Aug 27 2026). An early dump showing bare "Copy" buttons on this surface had simply been hovered beforehand — a fresh response exposes only the toggle, which is why copy-button counting alone times out here. The toggle has exactly the mount timing detection needs: the echoed user message's toggle appears right after sending, the in-flight response contributes nothing while the Stop button shows, and the response's toggle mounts in the same beat the Stop button disappears. The relay therefore counts "message affordances" (mounted copy button or collapsed toggle — one per message, `messageActionsLabel` in `Core/Config.swift`) and expands the newest toggle via AXPress before copying. One trap: a "Send feedback" button matches the bare send keyword — `sendExcludeKeywords: ["feedback"]` exists solely to dodge it. Unused signal worth knowing: the sidebar's session buttons carry state as `AXTitle` prefixes ("Running …", "Idle …", "Awaiting input …"), a direct completion cross-check — but only while the sidebar is expanded: collapsing it removes those buttons from the tree entirely (the header button keeps just the bare session title, no state), leaving an "Open sidebar" button as the tell (and a way to restore the signal programmatically). Note the tree only carries the *displayed* conversation: a session running in the background contributes no Stop button and no transcript affordances. Verified idle from an independent shell (Aug 27 2026): the composer toolbar announces the session's model and effort as two **adjacent** `AXPopUpButton`s — a bare-titled model ("Fable 5") immediately followed by "Effort: Extra" — and the strip reads the pair via `effortPopupPrefix`: the effort match claims the popup visited just before it as the model, composing "Fable 5 · Extra". A "Usage: context N, plan N%" popup sits alongside, unused but worth knowing.
- **The composer's drawn field** (live, Sep 12 2026, `swift tools/ax-dump.swift claude --prompt-geometry --frames`): the group that holds the text area and its controls sits 8 px inside the box the app draws, on Claude's chat composer (the text row with the attach popup, Chat/Cowork toggle, and dictation controls; the project and model row hangs outside beneath it) and on Claude Code (the text row with its Send/Stop control; the repository chips above and the +/mode/model toolbar below are outside the box). ChatGPT's box is the group with the buttons as direct children, and the band around it grows sideways only. `promptTransferGeometry` widens the nearest shell through wrappers that only pad it uniformly, so the transfer outline and the setup drop area trace the drawn border instead of the row inside it.
- **Chat vs Cowork vs Code** (verified live, Aug 27 2026): the Chat and Cowork views share one window, one URL (`claude.ai/new`), one composer label ("Write your prompt to Claude"), and one sidebar — none of those distinguish them, so the strip's URL-based surface naming cannot either. Note the current Claude Desktop build is single-window — there is no File > New Window, and Chat, Cowork, and Claude Code swap in place inside the one window via the world switcher — so the multi-window scoping story above describes an older build, and "no chat window open" is simply what the Code world always looks like. The real signals are two `AXRadioGroup` pairs, each with `AXValue` 1 on the active option: a top-level pair switching worlds (`AXDescription` "Chat and Cowork" vs "Code, …" — either label can append live session state, e.g. "Code, awaiting your input" and "Chat and Cowork, awaiting your input", so match the name before the comma) and a composer-level pair (`AXTitle` "Chat" vs "Cowork"). The top-level pair is what window exclusion reads; note that both options are always mounted, so `AXValue` is the only thing separating them and a label-only match would exclude every Claude window. Fallback markers if the radios move: a "Use incognito" button exists only in Chat, "Clear active" only in Cowork. The active model is readable on the Chat and Cowork surfaces from the `AXPopUpButton` whose `AXDescription` starts with "Model: " (e.g. "Model: Fable 5 · Extra"; Cowork showed "Model: Opus 5 · Extra"), name and effort level in one label; the readiness strip shows it next to the surface. Claude Code has no "Model:"-prefixed popup — it splits the announcement into the bare-model + "Effort:" popup pair covered in the fallback bullet above (a "Model:" popup observed on Code right after a surface switch was the chat composer still mounted mid-transition — re-dump after transitions before trusting a first observation); ChatGPT's model pill is covered in its own bullet. Caveat on self-observation: every agent-shell dump of the window hosting the agent's own session necessarily happens mid-turn, so that session's idle-state tree can never be captured from inside it.
- **Message numbering and list virtualization** (verified live, Aug 28 2026, from a relay run that hung): Claude renders each conversation message as an `AXGroup` (subrole `AXDocumentArticle`) named "Message N" — an absolute ordinal, user and assistant messages alike, delivered in `AXDescription` with an empty `AXTitle`. In long conversations the list is **virtualized**: only the last few messages stay mounted (the stuck window held "Message 6"–"Message 8" of 8; one of their "Message actions" toolbars was rendered 1px tall, half-clipped), so the affordance count falls as responses land and any count-above-baseline wait deadlocks. The newest message is always mounted, making the highest ordinal a monotonic completion signal (`lastMessageOrdinal`); the echo bumps it once and the response again, so completion is baseline+2 where echoes register. Verified on the Claude Code surface; whether the chat surface numbers messages the same way is unobserved — if it does not, chat falls back to the count and the streaming transition. Expanded action bars on this surface also put "Rewind to here" inside per-user-message toolbars, which is one of the `windowExcludeLabels` — that hover-dependent marker used to be the only thing classifying the window, and the world switcher now carries that job (see the window-scoping bullet above).
- The "Stop" label during streaming has not been observed live on either app's *chat* surface yet; on short conversations the echo-absorbed copy-button count detects completion there, and the virtualization hang has only been observed on the Claude Code surface so far — but nothing suggests the chat surfaces render unbounded lists, so assume long chat conversations need the ordinal or streaming-transition signal too. (Claude Code's running-state "Stop" button *has* been observed live — see above — so the streaming-transition backstop is real on that surface; on the chat surfaces it is unverified until streaming is captured there.)
- A run always seeds into whatever conversations are already open; opening a fresh chat on each side is the operator's job, deliberately, since Errol typing into the wrong conversation is worse than it starting in the last one. Beware "Continue in new chat" in ChatGPT, which carries prior context into the new conversation and leaves stale copy buttons in the tree — the affordance baseline then starts high, so open a genuinely fresh chat between runs.
- Surface detection for the readiness strip: ChatGPT's `Switch mode, current mode: <mode>` popup and Claude's `/epitaxy/` web-area URL (a Claude Code session) are verified against live trees (Aug 2026). The claude.ai path names for regular chats, new chats, and project chats in `surfacePathNames` are expected values that have not been observed yet — an unknown path shows up raw in the strip, which is the cue to add it to the map in `Core/Config.swift`.
- Selectors are label-based and will break when either app renames or icon-ifies its buttons after an update. Non-English UI needs the keywords in `AppSelectors` changed.
- OpenAI's app naming is mid-migration: the unified app can be named ChatGPT.app while identifying as `com.openai.codex`, with a "ChatGPT Classic.app" as `com.openai.chat`. `osascript -e 'id of app "ChatGPT"'` shows what this machine actually runs.

## Troubleshooting

- **App "not running" but it is**: bundle ID mismatch. Check with `osascript -e 'id of app "ChatGPT"'` and adjust the IDs in `Core/Config.swift`.
- **Empty tree / no buttons found in Inspect**: quit and relaunch Errol so the `AXManualAccessibility` nudge reapplies; confirm with `swift tools/ax-dump.swift <app> --buttons`.
- **Wrong button pressed (e.g. "Copy code")**: adjust `copyExcludeKeywords` in `Core/Config.swift`.
- **"Paused: … window isn't showing"**: the connected window is minimized, or ("behind another ChatGPT window") could not be brought in front of the app's other windows before typing; bring it forward, or close what is over it. The log's `targeting` line at connection (and again at Send) names the conversation each window showed when it was connected; what it shows later is not compared.
- **"Paused: … has an unsent draft" on an empty composer**: the composer's AX value did not match the shared placeholder list (`composerPlaceholders` in `Core/Config.swift`) or the element's own label after an app update changed its placeholder text; click into the field and add the new text to the list. "Paused: … is replying" on an idle conversation is the sidebar-title hazard from the open threads above wearing another hat: the same `hasStopButton` scan that keeps the wait alive there feeds the composer guard, so a sidebar conversation titled "Stop …" also refuses the start and holds every delivery until it is renamed or the sidebar is collapsed.
- **"clipboard never changed after pressing copy"**: the copy button was pressed while the app's window was unfocused, so its renderer refused the clipboard write. The copy path activates the app first and retries once, so a run reaching this has failed both attempts — check the focus report logged beside it for who held focus instead.
- **A message lands twice in the composer** (the same text twice, or two pasted-text chips): the paste receipt was not observed within two seconds and `send` pasted again on top of a paste that had in fact landed. The receipt is the payload's opening letters and digits in the composer's AXValue (fence lines skipped, since ChatGPT renders them away), a new attachment chip counted under the composer container, or the composer growing by a third of the payload; and a retry is only made while the composer stands exactly as it did before the keystroke, so a doubling now means the composer was unchanged after the first paste and changed after the second — worth a look at what the app did in between. Open the run's debug log (**Show Debug Logs in Finder**) and read the `expecting`, `paste watch`, and `paste miss snapshot` lines for that attempt: they say what the composer held before and after, whether the value read failed (a rebuilt composer element answers invalidUIElement), whether the needle was found, how far the composer grew, and whether a chip's remove button mounted somewhere other than the ancestor level `pastedTextAttachmentAncestorLevels` names, with its actual label. The JSON captures beside the log turn into a fixture for a failing test.
- **Paste lands but Return doesn't send**: some layouts use Cmd+Return; change `keystroke(keyReturn)` to `keystroke(keyReturn, flags: .maskCommand)` in `send(_:to:)`.
- **Start silently does nothing after a rebuild**: the privacy system treats a re-signed build as a new app; re-toggle Errol (or Xcode, for Xcode-launched runs) in System Settings > Privacy & Security > Device Control and Data Access (Accessibility before macOS 27).
